# Bridge Gateway - Render.com support notes

## Why this works

The gateway is a single Go binary backed by SQLite (modernc.org/sqlite, pure Go,
no CGO) and an in-memory cache. Render does not need a database, cache, or
worker box: one Web Service with a Docker build is enough. There is no
`compose.yml`/Postgres/Redis dependency to remove.

## What was changed

### Entry point & port (`main.go`)
- The listening port is resolved by `infrastructure.ResolvePort`, which already
  respects Render's `BRIDGE_PORT` environment variable and keeps the explicit
  `--port` flag in front of it.
- `http.Server` has `Read/Write/IdleTimeout`, listens on `:PORT`, and shuts down
  gracefully on `SIGINT`/`SIGTERM`, so Render's stop signal is handled cleanly.
- `ONNX_AUTO_DOWNLOAD=0` disables the first-run ONNX artefact download; useful
  for an offline image. The image does not bundle `models/` (gitignored), so the
  default keeps the download enabled.
- `BRIDGE_DB` overrides `--db` (SQLite file path); `BRIDGE_PORT` is the value
  Render's UI sets.

### Build (`Makefile`, `Dockerfile`)
- `make build` and `make build-linux` compile with `CGO_ENABLED=0` for
  `linux/amd64` / `linux/arm64`; these targets are for local native runs only.
- The `Dockerfile` is a multi-stage build: a **glibc** `golang` builder
  cross-compiles the `linux/$TARGETARCH` binary from the repo sources, and the
  runtime is a minimal **Debian** (glibc + `ca-certificates`) image. `scratch`
  is not usable: the purego-loaded ONNX runtime imports `libdl.so.2` /
  `libc.so.6`, so the binary is dynamically linked to glibc. Render's
  auto-detect picks up this `Dockerfile` and builds the same way — from a clean
  clone, with no prebuilt binary, `certs/` or `models/` required.
- The builder must be glibc-based too: for a dynamically linked binary the Go
  linker records the ELF interpreter of the **build host** (it falls back to
  `/lib/ld-musl-<arch>.so.1` when `/lib64/ld-linux-x86-64.so.2` is absent, i.e.
  inside Alpine). An Alpine builder therefore produced an image that could not
  start on the Debian runtime — `exec /bridge-gateway: no such file or
  directory`, ENOENT on the missing interpreter. The runtime stage now runs
  `/bridge-gateway --help` once at build time, so any binary/image mismatch
  fails the build with a readable error instead of the deploy.

### On Render
1. Create a **Web Service**, point it at this repository, and select
   **Docker** as the runtime.
2. Add the environment variables: `BRIDGE_PORT=4000`, `BIFROST_MASTER_KEY`
   (in clear text, it stays in process), and leave `ONNX_AUTO_DOWNLOAD` enabled
   (`1`) so `models/onnx/` is fetched at first start — set it to `0` only for an
   offline image.
3. For Ollama in Render, set `OLLAMA_HOST=http://10.0.0.1:11434` (or the
   internal DNS of the Render host running Ollama) and deploy the Ollama box
   first so the gateway can reach it.
4. Start the service on `:4000`; the Web UI is at
   `https://<app>.onrender.com` (HTTP only, no SSL PEM bundle is embedded).

## Build / verify locally

```bash
make build          # host binary
make test           # go test ./tests/ -v -count=1
make docker-up      # build the image (compiles inside Docker) + run

# Equivalent raw build of the deployment image (Render:
# linux/amd64 on amd64 hosts, linux/arm64 on arm64 hosts):
podman build -t bridge-gateway .
```
