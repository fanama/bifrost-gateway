Le problème

Trois taxes d'intégration, payées par chaque équipe qui livre une fonction LLM.

01

Dispersion des providers

Dix backends, dix schémas d'authentification, dix formats d'erreur. Chaque équipe réimplémente streaming, retries et comptage.

02

Réponses sans preuve

Le modèle ne cite que ce qui atteint son contexte. Un dossier de PDF n'est pas une citation ; une réponse plausible n'est pas une source.

03

Le RAG ajoute un service

Un vector store, c'est un credential, une sauvegarde et une panne de plus à surveiller — un autre système dont dépend une réponse.

La contrainte n'est pas d'ajouter des providers : c'est de faire du retrieval sans ajouter de service.

Bridge Gateway · présentation2 / 18
La réponse

Un processus, une clé, un contrat de retrieval.

  • API OpenAI-compatible : /v1/chat/completions, /v1/embeddings, /v1/models. Les clients changent une base URL.
  • BifrostAI embarqué comme bibliothèque : aucun proxy HTTP dans le chemin.
  • RAG sous /v1/rag/*, avec la même clé, scopé au projet qui la possède.
  • Chaque retrieval déclare sa méthode : graphe HNSW ou scan exact, avec degraded dans la réponse.
0 service externe requis pour tourner : SQLite, cache en mémoire et runtime ONNX vivent dans le processus.

Bridge Gateway · présentation4 / 18
Garde-fous

Chaque règle existe à cause d'une manière précise de se tromper.

01

Le projet vient de la clé. La master key est refusée sur /v1/rag/* : une clé ne peut pas lire le corpus d'un autre tenant.

02

Même espace vectoriel. Un passage n'est classé que si son modèle et sa largeur correspondent à la requête ; sinon on compare des espaces étrangers.

03

Une panne d'index n'est jamais un 5xx. Tout état non prêt bascule sur le scan cosinus exact et l'annonce avec degraded: true.

04

Une suppression est visible avant la réponse. Les tombstones filtrent les passages au query time ; un document supprimé ne peut pas réapparaître.

Bridge Gateway · présentation9 / 18
Retrieval

La recherche dit toujours ce qu'elle a réellement fait.

  • dense : HNSW par projet ; à froid, en construction, en dépassement ou en erreur → scan cosinus exact.
  • hybrid : BM25 sur les mêmes passages, fusion par Reciprocal Rank Fusion ; un acronyme ou une référence ne se perd pas.
  • MMR optionnel : lambda 0,1–1 (défaut 0,7), pool de candidats au moins égal à top_k.
  • Le graphe n'est jamais persisté : reconstruit depuis SQLite au démarrage ; les suppressions sont des tombstones.
1 graphe par projet, avec son propre budget mémoire (64 MB par défaut).

Chaque réponse expose l'état de l'index et degraded. Un fallback n'est pas une erreur cachée : c'est un champ lisible.

Bridge Gateway · présentation10 / 18
Données et sécurité

Un seul fichier à sauvegarder, et une chose volontairement absente.

  • 8 tables : projets, configurations, clés, providers, modèles, réglages RAG, documents, chunks.
  • Lignes uniformes : (id, payload JSON), avec index JSON sur les champs filtrés.
  • Clés API : SHA-256 seulement ; le secret en clair n'existe qu'à la création.
  • Le graphe HNSW n'est pas persisté : il se reconstruit depuis les vecteurs stockés.
  • Caches bornés : lectures 15 s / 2 048 entrées ; réponses LLM 5 min / 512.
  • Import JSON legacy idempotent : les IDs existants gagnent, les fichiers importés sont renommés .imported.

Modèles et routage

Local par défaut, cloud par configuration.

  • Embeddings par préfixe : onnx/… → runtime local, local/… → embedder déterministe, sinon Bifrost.
  • Défauts hors ligne : all-MiniLM-L6-v2 (384 dimensions) et SmolLM2 135M.
  • Tiers fast < balanced < frontier, classifieur local granite4:tiny-h, confiance minimale 0,6.
  • Échec d'un tier : montée d'un cran, refroidissement 60 s, timeout classifieur 10 s.
off routing désactivé par défaut : le classifieur est sur le chemin critique de chaque requête non cachée.

Rate limit, quota, contexte, panne et credential rejeté sont retryables ; validation et annulation ne le sont pas.

Exploitation

Le conteneur construit un binaire qu'il peut réellement exécuter.

  • Deux étages glibc : builder golang, runtime debian:bookworm-slim + CA.
  • Pas de scratch ni Alpine : purego charge l'ONNX Runtime via libdl/libc ; un loader musl casse au démarrage.
  • Garde au build : le runtime exécute le binaire une fois ; un mismatch d'architecture échoue au build, pas au déploiement.

Bridge Gateway · présentation15 / 18
Limites

Ce que ce n'est pas, dit aussi clairement que le reste.

  • Mono-processus. Deux instances sur le même fichier SQLite construisent chacune leur graphe : correct, coûteux, non supporté.
  • Index en mémoire. Après un redémarrage, les premières requêtes utilisent le scan exact jusqu'au rebuild.
  • Cible ≤ 10 000 chunks par projet. Au-delà, les hypothèses de recall et de latence ne tiennent plus.
  • Défauts HNSW provisoires. M, efConstruction et efSearch n'ont pas de benchmark commité ni de gate CI.
  • Scans et fichiers Office exclus. Un PDF sans couche texte est refusé, pas indexé comme du bruit.
  • Pas d'éviction entre projets. Chaque plafond est par projet, donc les graphes inactifs restent résidents.
