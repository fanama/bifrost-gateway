The problem

Three integration taxes, paid by every team that ships an LLM feature.

01

Provider sprawl

Ten named backends, ten auth schemes, ten error shapes. Each one re-implements streaming, retries and usage accounting behind its own SDK.

02

Answers without evidence

The model can only cite what reached its context. A folder of PDFs on disk is not a citation, and a plausible answer is not a source.

03

Retrieval means a new service

Vector search usually arrives as another store: another credential, another backup, another failure domain to page someone about.

The hard constraint here is not adding providers — it is doing retrieval without adding a service.

The answer

One process, one key format, one retrieval contract.

  • OpenAI-compatible /v1/chat/completions, /v1/embeddings, /v1/models: existing clients change a base URL.
  • Bifrost embedded as a library — no proxy hop, no extra socket in the path.
  • RAG on the same key under /v1/rag/*, scoped to the key's project.
  • Retrieval states its own method: HNSW or exact scan, with degraded and index_state on every response.
0 external services required to run. SQLite file, in-process cache, in-process ONNX runtime.

The path a user takes

Four steps from an empty install to a cited answer.

01

Create a project

Add a provider and an active configuration. Model, prompt, tier and response format live there.

02

Issue a key

The secret is shown once. Only its SHA-256 digest is stored, and it only ever sees its own project.

03

Upload documents

Text, Markdown, HTML, CSV, JSON, YAML, XML, PDF, images. PDFs are parsed into Markdown; images are transcribed.

04

Ask

Post a question to /v1/rag/query or use the test bench; get an answer with source passages.

Uploads are synchronous: when the request returns, the passages are stored, embedded and indexed.

Bridge Gateway · technical brief4 / 18
Guardrails

Every rule here exists because of a specific way this goes wrong.

01

The project comes from the API key. The master key is rejected on /v1/rag/*, so a key cannot retrieve another tenant's corpus.

02

Vectors must share a space. A chunk is only ranked when its embedding model and width match the query vector — otherwise unrelated spaces get compared.

03

An index failure is never a 5xx. Cold, building, mismatched, over capacity or errored all fall back to the exact scan and say so with degraded: true.

04

Deletes are visible before the response. Tombstones hide a document's passages at query time, so a deleted file cannot resurface.

Ingestion

Format handling is where retrieval quality is actually won.

PDF

Page → Markdown

Headings from font size, list items from bullets and indentation, paragraphs re-glued across line breaks, hyphenated words reattached. Pure Go — no Poppler, no Java.

Images

Pixels → text

Transcribed by the active configuration's vision model, in reading order, with a short factual description when the image carries no text.

Chunks

Boundary-aware

Chunking targets the configured size but snaps to the nearest paragraph or line, so Markdown structure survives into the passage.

Limits are explicit: 25 MiB per upload; Office files rejected; a scanned PDF with no text layer is rejected rather than indexed as noise.

Under the hood · technical

The index is a derived cache that is allowed to fail.

  • One graph per project, pure Go, no CGO — the dependency constraint was hard.
  • Vectors are L2-normalized on insert, so inner product is cosine; returned scores are recomputed exactly.
  • M=16, efConstruction=200, efSearch=64 — provisional defaults, per the spec's decision log.
  • Writes are visible immediately: upsert happens before the upload returns; the next search sees it.
  • Deletes tombstone nodes, filtered at query time; a rebuild is scheduled at 20% tombstones.

graph.go · insert.go · search.go
manager.go · build.go

Fallback contract: cold · building · model or width mismatch · over capacity · build error → exact cosine scan, degraded: true, never a 5xx.

Memory is estimated per node: vector bytes + text + 128 B metadata + 4 B per link; the default cap is 64 MB per project.

Index lifecycle

What the caller sees, in each state.

Every state advertises itself on the response, and every non-ready state answers from the exact cosine scan. A query whose embedding model or width differs from the graph scans exactly for that request and starts a rebuild. Arithmetic, not a benchmark: 10,000 chunks × 384 dimensions × 4 bytes = 15.4 MB of vectors, before links and metadata.

Bridge Gateway · technical brief10 / 18
Data handling

One file to back up, and one thing deliberately not in it.

  • Eight tables — projects, configurations, API keys, providers, catalog models, RAG settings, documents, chunks.
  • Uniform rows: (id TEXT PRIMARY KEY, payload TEXT) with JSON payloads and JSON indexes on filtered fields.
  • Keys are digests: only SHA-256 is stored; the plaintext secret exists once, at creation.
  • The graph is never persisted. It is rebuilt from stored vectors, so a schema change cannot corrupt it.
  • Two bounded caches: repository reads 15 s / 2,048 entries; LLM responses 5 min / 512 entries.
  • Legacy JSON import is idempotent: existing IDs win, imported files are renamed .imported.

Isolation

The project is the tenant boundary for everything.

Scope

Config, keys, corpus

Every configuration belongs to a project. One active configuration per project; keys authenticate /v1/* against it.

Index

One graph, one cap

Each project gets its own graph and its own memory budget, so one large corpus cannot evict another project's index.

Rules

Validated in the domain

top_k 1–20, M 16–64, efConstruction 40–2000, tombstone ratio 0.05–0.50, memory 8–1024 MB.

Settings live as one JSON payload per project; missing fields normalize to defaults, so the index parameters needed no SQL migration.

Models and routing

Local by default, cloud by configuration.

  • Embeddings route by name prefix: onnx/… to the local ONNX runtime, local/… to a deterministic embedder, anything else to Bifrost.
  • Defaults run offline: all-MiniLM-L6-v2 for embeddings, SmolLM2 135M for local chat.
  • Tier ladder fast < balanced < frontier, chosen by a local classifier at a 0.6 confidence floor; a failing tier cools down for 60 s.
~25 s cost of using gemma4:e4b as the routing classifier on this setup — documented in config.yaml. A small model takes a fraction of a second.

Routing is disabled by default: the classifier runs on every uncached request, so its latency is on the critical path.

Operational story

The container builds a binary it can actually run.

  • Two stages, both glibc: a bookworm builder cross-compiles with CGO_ENABLED=0; the runtime is debian:bookworm-slim plus CA certificates.
  • Why not scratch or Alpine: purego loads the ONNX runtime through libdl and libc, so the binary is dynamically linked; an Alpine builder recorded a musl loader and the container died with exec: no such file or directory.
  • Build-time guard: the runtime stage executes the binary with --help, so an architecture or interpreter mismatch fails the build, not the deploy.

Bridge Gateway · technical brief15 / 18
Limits

What this is not, stated as plainly as the features.

  • Single process. Two instances on one SQLite file each build their own graph — correct, wasteful, and explicitly unsupported.
  • In-memory only. After a restart the first queries use the exact scan until the background rebuild finishes.
  • Scoped to ≤ 10,000 chunks per project. Above that the spec's recall and latency assumptions no longer hold.
  • Defaults are unbenchmarked in the repo. M, efConstruction and efSearch are provisional; the 99% recall target has no committed measurement and no CI gate.
  • Scans and Office files are out. A PDF without a text layer is rejected; DOCX and XLSX are refused outright.
  • No cross-project eviction. Each cap is per project, so idle graphs stay resident.

Next steps

Three priorities, in the order the evidence demands.

01

Measure recall, then freeze defaults

Run the spec's manual benchmark against exact search on a 10k-chunk corpus, and record the winning parameters. Everything else tunes around this number.

02

Put the index on the dashboard

Build time, node and tombstone counts and the fallback rate already exist per project; aggregating them turns "degraded" from a field into an alert.

03

Decide the multi-instance topology

Either a shared index or per-instance graphs with a documented trade-off. Today the honest answer is one process, one file.

Order matters: the recall figure determines whether the graph, the chunker or the embedding model is the thing worth changing next.
